Why this page does not show a fake application table

PrimePay V1 currently exposes business creation and the authenticated merchant's own business information, but it does not expose an administrator endpoint for listing, reviewing, approving, or rejecting all merchant applications. Showing invented rows here would make the dashboard look impressive while making the software fundamentally dishonest. Humanity has enough of that already.

Merchant verification workflow

The intended operational path supported by the current business model.

01

Business registration

A merchant creates an account and submits their business profile through the onboarding flow.

02

Verification

The Business record carries a verification status: pending, approved, or rejected.

03

Live API review

Live API access is controlled separately through the business verification and live API flags.

04

Activation

Once approved and enabled, the merchant can progress toward production API access.

Current V1 capabilities

What the backend actually supports today.

B

Business records

Merchants can create their business profile and retrieve their own business information.

✓

Verification state

Business records contain verification status and live API eligibility fields.

K

API access control

Live API key creation is restricted by business approval and live API enablement.

⌁

Application management API is not exposed yet

The frontend is ready for this capability, but the backend needs administrator endpoints before real application data, review actions, filters, pagination, approval, rejection, and audit history can be connected safely.
