This interface therefore keeps the operational design ready without fabricating merchant records.

Merchant registry is not exposed by the current V1 API

The current backend provides POST /api/v1/businesses, GET /api/v1/businesses/me, and GET /api/v1/businesses/balance. These endpoints are scoped to the authenticated merchant. There is currently no administrator endpoint for listing every business, searching merchants, opening a merchant profile, suspending a business, approving verification, or changing live API eligibility.

Administrative security principles

Merchant management should remain server-authoritative.

01

Never trust frontend state

The browser should display the backend's merchant state. It must never decide that a merchant is approved, suspended, or production-ready simply because somebody changed a JavaScript variable.

02

Protected administrator routes

Merchant-wide queries and mutations should require JWT authentication plus administrator authorization on the backend.

03

Auditable changes

Approval, rejection, suspension and production-access changes should produce durable audit events rather than disappearing into the browser like so many questionable human decisions.

04

No secret exposure

Merchant API secrets, passwords and other sensitive credentials must never appear in merchant registry responses or ordinary administrative tables.

M

Merchant registry backend is the next missing piece

The frontend structure is now prepared for a real merchant registry. To activate it, PrimePay needs administrator-only business endpoints for listing, searching, filtering, pagination and merchant detail retrieval, followed by protected mutation endpoints for verification and account operations.
